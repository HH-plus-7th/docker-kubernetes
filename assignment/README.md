# Frontend Docker Communication Challenge 심화편

## 과제 목적

이 과제는 프론트엔드 런타임 아키텍처 심화편입니다.

평가하려는 것은 다음입니다.

- 브라우저 네트워킹과 Docker 네트워킹의 차이 이해
- CORS와 credentialed request 이해
- HttpOnly 쿠키 기반 인증 흐름 이해
- SameSite / Secure 제약 이해
- 프론트엔드 production runtime 구조 설계 능력
- 환경 분리와 dev / prod 차이 설명 능력
- 아키텍처 선택과 디버깅 reasoning

이 과제는 백엔드 과제가 아닙니다.
이 과제는 데이터베이스 과제가 아닙니다.
이 과제는 일반적인 Docker 입문 과제가 아닙니다.

백엔드 API와 데이터베이스는 이미 구현되어 있으며, 과제에서는 black box로 취급해야 합니다.
코드를 읽어 맥락을 파악하는 것은 가능하지만, 제출물에서 백엔드나 데이터베이스 앱 로직을 수정하면 안 됩니다.

## 시나리오

여러분은 겉보기에는 단순한 쇼핑몰 프론트엔드를 받게 됩니다.
하지만 실제 브라우저 정책, 쿠키 인증, 컨테이너 런타임 조건이 들어오면 이 앱은 기대한 대로 동작하지 않습니다.

백엔드는 HttpOnly 쿠키 기반 인증을 사용합니다.
여러분의 목표는 프론트엔드를 Docker 환경에서, 실제 브라우저 조건을 만족하면서, production 스타일 런타임으로 정상 동작하게 만드는 것입니다.

중요한 것은 "한 번 되게 만들었는가"가 아닙니다.
왜 실패했는지, 왜 최종 구조가 동작하는지, 어떤 trade-off를 선택했는지를 설명할 수 있어야 합니다.

## 제공되는 것

- 실제 동작하는 백엔드 소스
- 실제 동작하는 DB 스키마 및 시드 설정
- API 계약 문서
- 테스트 계정
- 의도적으로 깨진 프론트엔드 starter

## 금지 사항

- 백엔드 앱 로직 수정
- 데이터베이스 스키마 또는 영속성 로직 수정
- 문제 해결을 위한 백엔드 기능 변경 요청
- 서버 비즈니스 로직을 바꿔서 문제를 우회하는 방식

## 허용 사항

- 프론트엔드 코드 수정
- Docker 관련 파일을 처음부터 직접 작성
- 프론트엔드 런타임 서버 또는 reverse proxy 구성
- 요청 전략 및 환경 처리 방식 변경
- 아키텍처 선택과 trade-off 문서화

## 구현해야 하는 사용자 흐름

최종 결과는 다음 흐름을 모두 만족해야 합니다.

- 로그인
- `/api/auth/me`로 현재 사용자 조회
- `/api/products`로 상품 목록 조회
- `/api/cart`로 장바구니 조회
- `POST /api/cart/items`로 장바구니 추가
- 브라우저 새로고침 후에도 인증 유지

## 제출물

반드시 제출해야 하는 파일:

- `Dockerfile`
- `docker-compose.yml`
- `.dockerignore`
- `README.md`
- `ADR.md`

추가로 만들어도 되는 파일:

- `nginx.conf`
- runtime config 파일
- `.env.example`
- 아키텍처 설명에 필요한 기타 문서

## 최종 통과 조건

제출물은 다음 조건을 모두 만족해야 합니다.

- `docker compose up --build` 로 전체 스택이 정상 실행된다
- 프론트엔드가 브라우저에서 접근 가능하다
- 브라우저에서 로그인에 성공한다
- 로그인 이후 인증이 필요한 후속 요청이 정상 동작한다
- 장바구니 동작이 정상 동작한다
- 새로고침 후에도 인증 상태가 유지된다
- 브라우저 콘솔에 CORS 에러가 나타나지 않는다
- 최종 런타임이 production frontend build를 사용한다
- dev server에만 의존하지 않는다
- 백엔드/DB 앱 로직 수정 없이 해결된다

## 평가 포인트

- 아키텍처 결정의 품질
- trade-off 분석의 품질
- Docker 및 런타임 구성의 품질
- 브라우저 / 네트워크 이해도
- 인증 흐름 이해도
- 문서화와 설명의 품질

## 검토 질문

과제를 마친 뒤 아래 질문에 명확히 답할 수 있어야 합니다.

1. `backend:3000` 은 왜 Docker 내부에서는 보이는데 브라우저에서는 실패하는가?
2. 로그인은 성공한 것처럼 보이는데 `/api/auth/me` 는 왜 실패할 수 있는가?
3. `credentials: 'include'` 는 실제로 무엇을 바꾸는가?
4. reverse proxy 는 왜 이 문제를 단순화할 수 있는가?
5. 이 과제에서 same-origin 과 same-site 의 실질적인 차이는 무엇인가?
6. 왜 어떤 구성은 개발 환경에서는 되고 production 에서는 실패하는가?
7. 어떤 아키텍처를 선택했고, 그에 따른 trade-off 는 무엇이었는가?

## 시작 전에 알아둘 점

현재 starter의 깨진 동작은 의도된 것입니다.
일부 요청이 겉보기에는 동작한다고 해서 현재 구조가 올바르다고 가정하면 안 됩니다.
